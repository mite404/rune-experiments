Why this matters

Most desktop apps you've used are web pages in a box. Electron ships a whole browser, and Tauri borrows the system's. Rune doesn't draw with a browser at all. It lays out boxes with Taffy (the flexbox algorithm, in Rust), shapes text with Parley, and paints every pixel itself through wgpu, which talks to Metal on a Mac. The result is one native executable with no DOM, no CSS and no JavaScript runtime.

That changes what you need to know. In JS the browser decides when to repaint and the bundler hides compilation. In Rune you describe the screen as a pure function of your state, the framework diffs it and springs anything that moved, and cargo turns all of it (Rune, its dependencies, your code) into one machine-code file. Lesson 1 opens that box.

There's one more reason. Every Rune app can run headless: it renders PNGs and video and drives scripted input with no window. That's how you'll test it (Lesson 5), and it's how every recording on this page was made.

Background concepts

The whole model on one page

What is Rune? (First principles)

Picture a flipbook. Each page is drawn fresh from a description ("the switch is on, the knob is at the right"), and the animator never erases and redraws one line. Rune works the same way. You write one function that describes the whole screen from your data, and Rune calls it again whenever the data changes. In the jargon, this is a declarative, immediate-mode view with a retained diff. Rune keeps the previous page, compares, and animates what moved.

The pieces you'll use:

  • State (a struct you write). What: everything the app knows. When: created once by init and changed only by handlers.
  • view(&State, &mut Cx<State>) -> El. What: the screen as a tree of elements. When: Rune calls it after every change. Returns: the root El.
  • Builders: el(), row(), col(), text(..). What: make an El, then chain methods (.size(), .fill(), .child()…). Returns: El, by value, so every chain consumes and returns.
  • Handlers: .on_press(|s: &mut State| ..), .on_drag(..). What: the only place state changes. When: between frames, with exclusive access to the state.
  • AppSpec + rune::run. What: wires title, size, init, view and named scenes into a running app (window or headless).

Real-world analogy: a theatre lighting board. The cue sheet (state) says what should be lit, the board (view) turns that into fader positions, and the fade time (a spring) is how the lights get there. You never animate a fader by hand.

How one tap flows

1. view(&state)         → El tree      Calculation
2. layout + draw        → pixels       Orchestration
3. tap the switch       → on_press     Action
4. state.on flips       → new data
5. view(&state) again   → new El tree  Calculation
6. diff old/new by key  → knob x 2→18
7. spring, ~0.25 s      → it glides    Orchestration

Classification note. This course sorts every piece of code into one of three kinds, from Grokking Simplicity, plus two wiring roles:

DataThe footage in the vault. State, constants. Inert.
CalculationA colour-grade preset: same frame in, same frame out. view, knob_x.
ActionA live take: depends on when and how often. Handlers, poll.
OrchestrationThe edit: sequences takes, shoots nothing. Rune's frame loop.
MainThe director: one per film. fn main.

Prefer data to calculations, and calculations to actions. In Rune that rule is built in: the view is a calculation by type signature.

Compile your first app

A light switch, and the trip it takes from a .rs file to a program your Mac can run.

Terms in this lesson
Compile
In general: Translate source code into instructions a CPU runs directly, before the program runs.
In Rust: cargo build runs rustc on your crate and every dependency. Nothing runs until the whole program type-checks and borrow-checks.
Crate
In general: A package or library: a bundle of code you publish or depend on, like an npm package.
In Rust: The unit Rust compiles in one go. rune is a crate, your tutorial/ package is a crate, and each file in src/bin/ is its own small binary crate.
Binary / executable
In general: A file of machine code the operating system can launch.
In Rust: What cargo build writes to target/<profile>/<name>. A Rust binary carries all its Rust dependencies inside it.
Link
In general: The step that glues separately compiled pieces into one finished program.
In Rust: After every crate compiles, the linker joins them into one file and records the system frameworks it needs (AppKit, Metal).
Profile (debug / release)
In general: A preset of compiler settings for a build.
In Rust: dev (debug) compiles fast and runs slow. release optimizes. They're set in [profile.*] in Cargo.toml and write to different folders.
Struct
In general: A record type: named fields grouped together, like a JS object with a fixed shape.
In Rust: struct State { on: bool }. #[derive(Default)] asks the compiler to write a constructor that gives every field its zero value.
Borrow (&T / &mut T)
In general: Using a value without taking ownership of it, like lending a book.
In Rust: &State is a shared, read-only borrow, and many can exist at once. &mut State is exclusive and can change it. The compiler enforces this, which is why view can't modify state.
Closure
In general: A function you write inline that can use variables from around it.
In Rust: |s: &mut State| s.on = !s.on. Rust picks how it captures surrounding variables: by reference, by mutable reference, or by value with move.
Pure function
In general: Same input gives the same output, with no side effects.
In Rust: The tutorial calls these Calculations. Any fn that only takes &T or owned values and touches nothing global behaves this way.

Concept: compiling

Picture it first. Python is a live translator who reads your script aloud to the CPU, line by line, every time you run it. Rust is a translator who takes the whole book away and comes back with a finished edition in the CPU's own language. It's slower to get the first copy, but nobody needs the translator in the room after that.

What is it? Compiling turns source code into machine code: CPU instructions packed into an executable file (on a Mac, a Mach-O file). cargo is Rust's all-in-one tool. If you know Node, it's npm, tsc and your bundler in one:

JS / TSRust
package.jsonCargo.toml
package-lock.jsonCargo.lock (exact versions of every crate)
.nvmrcrust-toolchain.toml (pins compiler 1.99.1)
node_modules/~/.cargo/registry + ~/.cargo/git (sources)
dist/target/ (compiled output)
npm run buildcargo build --release
node app.jscargo run = build, then run the binary

Why? Rune draws 120 frames a second and does layout, text and springs on every one. That needs machine code, not an interpreter. You also want to hand someone a file that just runs.

How it works

cargo build downloads the source of every dependency (Rune, wgpu, winit, Taffy… several hundred crates), compiles each one, then compiles your code and links it all into one file. The first build is slow (1m 13s on our 6-core Mac). After that cargo reuses everything that didn't change, so a rebuild takes seconds.

There are two profiles:

  • debug (cargo build) → target/debug/. Fast to compile, slow to run, full of debug info. Ours measured 35 MB.
  • release (cargo build --release) → target/release/. Optimized: slower to compile, fast to run. Ours measured 24 MB.

Our Cargo.toml sets [profile.dev.package."*"] opt-level = 2, so dependencies stay fast even in debug. Debug GPU code without it is painfully slow.

Where programs come from. Cargo finds programs by folder. Every file in src/bin/ becomes a binary named after the file (l1_switch.rs → target/release/l1_switch). Every file in examples/ becomes one you run with --example. src/lib.rs is a library the others import as rune_tutorial.

Key: the file in target/release/ is the program. It links only to frameworks that every Mac ships with. We checked with otool -L: AppKit, Metal, CoreText and others, all under /System/Library. So it runs on another Apple-silicon Mac with no Rust installed.

Concept: state → view

Picture it first. A storyboard panel is drawn from the script, not from the previous panel. Change the script ("lights on") and the panel is redrawn to match.

What is it? State is Data, a plain struct with one bool. view is a Calculation: it borrows the state read-only (&State) and returns an El. It can't change anything, because Rust's borrow rules won't let it. on_press takes a closure that gets &mut State: that's the one Action.

Why? Because view is pure, Rune can call it as often as it likes, and you can call it in a test with no window (Lesson 5). Rust's types enforce the preference rule for you.

Three things on the switch you'll use in every lesson:

  • .key("knob"): a stable name. Rune matches old and new trees by key, so it knows this is the same knob that moved, not a new one.
  • .motion(motion::SNAPPY): changes in this subtree land on a 0.25 s spring. You change the number, and Rune animates it.
  • .role("switch").label("Lights").checked(s.on): what a screen reader announces ("Lights, switch, on"), through AccessKit. It's the same line of code, not a separate layer.

Why split it this way? knob_x is a Calculation pulled out of view. You can tell it's a calculation because it takes a bool, returns an f32 and touches nothing else. It's tiny, but it names the one number a spring animates, so Lesson 5's test can assert "lands 16 pt over" against knob_x(true) - knob_x(false).

Layout, keys, and a real .app

A music queue whose rows slide to their new places, shipped as an app with a name in the menu bar.

Terms in this lesson
Flexbox
In general: A layout model where a container lines its children up in a row or column and shares out the spare space.
In Rust: Rune runs the Taffy crate, a Rust port of CSS flexbox. row() / col() set the direction, and .grow(1.0) is flex-grow.
Identity (key)
In general: What makes "this" the same thing as "that" from one moment to the next.
In Rust: A string you attach with .key(..). Rune matches old and new element trees by key. In Rust code it's just a String, so build it from a field that never changes.
Slice (&[T])
In general: A view of a run of items in a list, without owning or copying them.
In Rust: &[Track] borrows part or all of a Vec<Track>. Functions take slices so any list can be passed in.
Iterator
In general: Something that hands you items one at a time.
In Rust: A value implementing the Iterator trait. Adapters like .filter, .chain and .copied build a pipeline, and .collect() runs it into a Vec.
Derive / Copy
In general: Having the compiler write boilerplate for you.
In Rust: #[derive(Clone, Copy)] lets a small struct be duplicated by a plain memory copy, so .copied() can turn &Track into Track.
move closure
In general: A closure that takes its own copy of what it uses, instead of pointing back at it.
In Rust: move |s| ... copies id into the closure, so the handler still works after this run of view ends.
Bundle / code signing
In general: Packaging a program with its metadata, and stamping it so the OS knows it hasn't been tampered with.
In Rust: Not Rust-specific. A .app is a folder around the cargo binary, and codesign signs it.

Concept: flex layout

Picture it first. A magazine page is a grid of stacks: a column of articles, each a row of photo and text. When a headline gets longer, the layout reflows instead of you nudging every block.

What is it? row() lays its children out left to right and col() top to bottom. Underneath is Taffy, a real CSS flexbox engine, so .gap(), .padding(), .center_y() and .grow(1.0) mean what gap, padding, align-items: center and flex: 1 mean on the web. .absolute(x, y) takes a child out of the flow (Lesson 1's knob used it).

Why? Each queue row needs the title on the left and the length and button pinned right, whatever the title's length. Once the words column grows into the spare width, that happens for free.

Gotcha.grow() is flex: 1 1 0: an element is only as big as the free space its parent leaves. In a column with no fixed height there is none. The same rule bites on the web.

Concept: keys

Picture it first. Actors on a stage wear name tags. When the director reshuffles the line-up, everyone walks to their new mark. Without tags, the stage manager would just repaint whoever stands in spot 1 to look like the new spot-1 actor.

What is it? .key(..) is that name tag. Between two views Rune matches elements by key, so a keyed row that moves from 4th to 1st travels on its spring. Without keys it matches by position, and every row's text just swaps in place.

Teach by negative space: keying a row by its index (format!("row-{i}")) looks right and is wrong. After a reorder, "row-0" is a different track, so nothing travels. The key has to come from something about the item that doesn't change: track.id.

Concept: a .app is a folder

Picture it first. A film print in its can: the reel is the movie, and the label on the can tells the projectionist what it's called and how to run it. The binary is the reel, and the .app is the labelled can.

What is it? A macOS application bundle is a directory that ends in .app, which Finder shows as one icon. Inside, Contents/MacOS/ holds your executable and Contents/Info.plist (XML) gives its name, bundle id, and which file to run. codesign --sign - adds an ad-hoc signature. Apple Silicon refuses to run unsigned code, and "ad-hoc" means signed, but by nobody in particular.

Why? cargo run starts a bare binary: no app name in the menu bar, no Dock identity, and nothing to double-click. Rune's own README says the same, and it ships scripts/mac-app for the full version with icons, URL schemes and live relaunch. Ours is a deliberately small version: 20 lines you can read.

When NOT to extract: the script is one straight line of steps used for one job. It has no functions, no config file and no options beyond the two arguments, so splitting it would add names without removing any complexity. Reach for scripts/mac-app when you need an icon or signing with your developer ID.

Springs and transitions

Three balls, three springs, one target, plus a word that knows how to arrive and how to leave.

Terms in this lesson
Spring
In general: A physics model that pulls a value toward a target and can overshoot and settle.
In Rust: rune::Spring, a small Copy struct built with Spring::new(duration, bounce). It's data you attach to an element, not a function you call.
const
In general: A named value fixed when the program is written.
In Rust: const LANES: [(&str, Spring); 3] is computed at compile time and inlined wherever it's used. Spring::new is a const fn, so it's allowed here.
Array vs tuple
In general: A fixed-length list of one type, vs a fixed group of mixed types.
In Rust: [T; 3] is three Ts. (&str, Spring) is a pair. Both have their size in the type.
Presence / transition
In general: How something animates when it appears and disappears.
In Rust: rune::Transition values, attached with .transition(..). Rune keeps a removed element drawn until its exit finishes.
Inheritance (in a tree)
In general: Children take a setting from their parent unless they set their own.
In Rust: Rune's .motion(..) flows down the element tree. This isn't Rust's type system, which has no class inheritance.

Concept: springs, not timelines

Picture it first. A door closer. You don't program the door's path: you set how stiff the closer is, and wherever you let go of the door, it swings shut along a natural curve. Push it mid-swing and it changes direction smoothly, with no jump.

What is it? A spring is a physical model that moves a value toward a target. Spring::new(duration, bounce) describes it in designer units: about how long it takes to settle, and how much it overshoots (0 = none). Rune's tokens are named springs: SNAPPY (0.25 s, 0), PLAYFUL (0.25 s, 0.15), SMOOTH (0.32 s, 0).

Why? A CSS transition restarts from the current value with zero velocity, so a fast double-tap looks broken. A spring keeps its velocity when the target changes (retargeting), and that's what makes motion feel physical.

Concept: transitions

Picture it first. An actor's entrance and exit, rehearsed separately: walk in from stage left, exit through the trapdoor.

What is it? An element that appears or disappears between two views has presence. .transition(..) says how it enters and exits. Transition::offset(0.0, 10.0).combined(Transition::opacity()) rises and fades. Transition::asymmetric(enter, exit) uses different moves for each (Lesson 4). Exiting elements stay drawn until their exit finishes, so you just delete them from the state.

Drag

Swipe-to-archive notifications: they follow your finger exactly, and let go decides their fate.

Terms in this lesson
Enum
In general: A type whose value is exactly one of a fixed list of options.
In Rust: enum Release { Archive, SnapBack }. Rust enums can also carry data in each variant, like Option<T>.
match
In general: Branching on the shape of a value.
In Rust: The compiler forces you to handle every variant, so adding a third Release breaks the build until every match handles it.
Option / let ... else
In general: "Maybe a value": either something or nothing.
In Rust: Option<T> is Some(t) or None. let Some(i) = ... else { return }; unwraps it or leaves the function early.
Gesture phase
In general: The stages of one touch: press, move, release.
In Rust: rune::Phase::{Down, Move, Up}, delivered in the Drag struct to your on_drag closure.
Threshold
In general: The cut-off value where behaviour flips.
In Rust: A plain const THRESHOLD: f32. Comparisons on f32 use >= and .abs().

Concept: a gesture has phases

Picture it first. A slingshot: grab, pull, release. What happens depends only on how far you pulled when you let go.

What is it? .on_drag(|s, d, tx| ..) runs once per phase of a pointer gesture: Phase::Down, then Move many times, then Up. d.dx/d.dy is how far the pointer has travelled since the press. Moves inside a drag land instantly, because the finger is the animation. The spring only takes over when you let go.

.offset(dx, 0) draws the card shifted without moving it in layout, so its neighbours hold still while you drag.

Why? Without phases you'd have to track "is the mouse down" yourself, which is state that goes stale the moment a release happens outside the window.

Teach by negative space: the tempting version puts if d.dx.abs() > 110.0 { remove } else { reset } straight in the Up arm. It works, and it hides your app's one real decision inside a closure that needs a live pointer to run. Pull it out into release(dx) -> Release, and the decision becomes a calculation you can test with one line (Lesson 5).

Testing without a window

Drive Lesson 4 with a fake finger and a fake clock, and assert on both the state and the screen.

Terms in this lesson
Unit test
In general: A small automated check that one piece of code does what it promises.
In Rust: A fn marked #[test]. cargo test builds a separate test binary and runs every one.
Attribute (#[...])
In general: A note to the compiler attached to the item below it.
In Rust: #[cfg(test)] compiles the module only for cargo test. #[derive(..)] and #[test] are attributes too.
Macro (name!)
In general: Code that writes code.
In Rust: Anything ending in !: assert_eq!, format!, todo!. They expand at compile time, which is how assert_eq! prints both sides when it fails.
Headless
In general: Running a program with no screen or window.
In Rust: rune::Runtime runs your real view, layout and springs in memory. Your test drives it frame by frame.
Dependency injection
In general: Handing a function the things it depends on (clock, input, network) instead of letting it fetch them.
In Rust: Rune passes dt, pointer events and now in as arguments, so a test can supply fake ones.
Mutation check
In general: Deliberately breaking the code to prove a test notices.
In Rust: Change >= to > in release and run cargo test. If nothing fails, the test isn't guarding that line.

Concept: a headless runtime

Picture it first. A flight simulator: the real cockpit software, real instruments, but the "sky" is supplied by the test rig, one frame at a time.

What is it? rune::Runtime::new(state, view, size, env) runs your real view and Rune's real layout, springs and hit-testing, with no window and no GPU. You are the clock: rt.frame(1.0 / 60.0) advances it one frame. You are the finger: rt.pointer_down/move/up(x, y). You read the results with rt.state (the data), rt.find(key) (an element's centre) and rt.presented(key) (its drawn rect, mid-spring included).

Why? It's dependency injection. The app never reads the time or the mouse itself: Rune hands both in. So a test can hand in fake ones and get the same result every run, in milliseconds, on CI.

Test what a user would notice: "the card is gone" and "it's drawn back home", not "dx was set to 0". Then a refactor of the internals doesn't break the tests.

Tests sit in a #[cfg(test)] mod tests at the bottom of the same file. Only cargo test compiles them, so they never ship in the binary.

GPU effects: fire

The view marks a box. A compositor paints fire into it on the GPU, and you steer it with four numbers.

Terms in this lesson
GPU / shader
In general: The graphics chip, and the small programs it runs for every pixel in parallel.
In Rust: Rust code talks to the GPU through the wgpu crate. The shaders themselves are written in WGSL, not Rust, and live inside rune-fx.
Compositor
In general: The stage that layers separate images into the final frame.
In Rust: A type that implements Rune's Compositor trait (src/gfx.rs). Rune calls its render every frame.
Trait
In general: A named set of abilities a type promises to provide, like an interface in TypeScript.
In Rust: impl Compositor<S> for Gfx { ... } gives Gfx the methods Rune needs, so run_with accepts it.
Module path
In general: The address of a name inside a project.
In Rust: rune_tutorial::gfx::FIRE is crate rune_tutorial (from src/lib.rs), module gfx, constant FIRE. use brings it into scope.
Integer vs float division
In general: Whole-number maths drops the fraction, and decimal maths keeps it.
In Rust: 1 / 3 on u32 is 0. Convert first with heat as f32 / 3.0.
Paint order / z-order
In general: What's drawn later covers what's drawn earlier.
In Rust: In Rune it's the order of .child(..) calls.

Concept: effect slots

Picture it first. A green screen on set. The actors (your UI) are filmed around a green rectangle, and in post the VFX house fills it with fire. The rectangle is cheap, and the fire is someone else's pipeline.

What is it? rune::effect(MARK) is an element that draws nothing. It just reserves a box in the paint order. A compositor (src/gfx.rs, adapted from Rune's showreel) runs every frame, finds each slot, reads its mark (which effect) and its .effect_data([f32; 4]) (four numbers), and asks rune-fx to paint that effect there with wgpu. .effect_bleed(pt) lets the effect draw outside the box. Flames rise far above a 24-pt slot. rune::run_with(spec, Gfx::default()) attaches the compositor.

Why? UI elements are rectangles, text and gradients. Fire is a fluid simulation. The slot lets the declarative view say where and how much, and leaves the how to a shader.

Paint order is z-order: later children draw on top. Put the log after the fire and it sits in front of the flames.

Read: the projector (src/gfx.rs)

You don't write this file. Read just two parts. The marks are Data, the contract between your view and the compositor. layer is a Calculation that turns one slot's mark and numbers into one rune-fx layer. The rest is the Action that talks to the GPU.

Two bugs we already hitA slot smaller than 1 pt sends NaNs into the shaders, so gfx.rs skips it. And software GPUs (a Linux VM's lavapipe) render these effects differently from Metal, so judge effects on real hardware.

Liquid glass

A glass pill that bends the stripes behind it, and a drop you can pull out that clings like water.

Terms in this lesson
Backdrop
In general: Whatever is already behind a thing.
In Rust: A copy of the frame drawn so far, which Rune hands to a slot marked .effect_backdrop(true).
Signed distance field / smooth union
In general: Describing a shape by "how far is this point from the edge", which lets two shapes blend like liquid.
In Rust: Inside rune-fx's shaders. You only pass shapes (Shape::circle, Shape::rounded) and a blend radius (union_k).
Transaction (Tx)
In general: One batch of changes applied together.
In Rust: &mut Tx comes into handlers. tx.instant() says to land this batch with no spring. Drag moves are already instant.
Named fields over tuples
In general: Labelling the parts of a value instead of numbering them.
In Rust: PILL.width reads better than PILL.2, so the lessons use a small struct Rect instead of a 4-tuple (Google's Rust style guide asks for this).

Concept: effects that read the backdrop

Picture it first. A magnifying glass on a newspaper. The glass has no picture of its own: it bends the print beneath it. Move the paper, and the glass shows the new print.

What is it? .effect_backdrop(true) marks a slot that needs to read everything drawn before it. Rune pauses the frame there, copies what's been drawn so far, hands the copy to the compositor, then carries on. The LENS effect refracts that copy through a bevelled shape. Give it a second circle and the two shapes merge with a smooth union, the gooey bridge you see when the drop is close. It's the same math that makes metaballs.

Why? A backdrop read costs a pause and a copy, so it's opt-in per slot. Ordinary slots never pay for it.

Effect data doesn't spring. Rune animates element properties (position, size, colour), but .effect_data([..]) is four raw numbers passed straight to the shader. Drag moves already land instantly (as in Lesson 4), and on release the drop jumps home. To make it glide you'd animate the numbers yourself from poll, which is Lesson 8's technique.

Gotcha we hitrune-fx's lens draws a drop shadow by default, and the shadow follows the goo: a dark rectangle trails the drop. gfx.rs sets shadow: 0.0. It only showed in a live window, not in still snaps.

Shockwave and the clock

Press a button and a ring of distortion ripples through every tile on screen.

Terms in this lesson
Frame loop
In general: The cycle that redraws the screen many times a second.
In Rust: Rune owns it. AppSpec::poll is your hook into each pass, with signature fn(&mut S, f64, &mut Tx) -> bool.
Side effect
In general: Anything a function does besides return a value, like reading the clock or writing state.
In Rust: poll takes &mut State and reads time, so it's an Action. Keep it tiny.
f64 vs f32
In general: Two sizes of decimal number. The bigger one is more precise.
In Rust: Rune's clock is f64 seconds, so it stays precise after hours. Shader data is f32, so you convert with as f32.
Duration
In general: A length of time, as opposed to a moment in time.
In Rust: std::time::Duration. Duration::ZERO passed to tx.wake_after means "next frame".

Concept: store when, not how far along

Picture it first. A stopwatch photo. You don't keep updating a note that says "the race is 3.2 s old": you write down when the gun went off, and anyone with a clock can work out the rest.

What is it? AppSpec::poll is a function Rune calls every frame with the current time. It's an Action (it depends on when it runs), and it's the only place your app touches the clock. Copy now into the state there. The handler records fired_at = s.now, and the shader gets fired_at and computes the ring's radius itself from the compositor's time. Strictly, that's Rune's animation clock, while poll gets wall time. They match while frames keep coming (which is why poll asks for them), but can drift if the window sits hidden for a long time.

Teach by negative space: the tempting design is a progress: f32 that poll nudges up every frame. It drifts if a frame is skipped, it needs a "done" flag, and it forces the view to rebuild 60 times a second. A start time is one number, written once. Rune only runs frames, and so poll, while something asks for them, so poll calls tx.wake_after(Duration::ZERO) to ask for the next one. Without it a press can stamp a stale now. poll returns false because nothing the view draws changed: the GPU animates on its own, since the compositor reports animating() = true.

DI again: because poll receives now instead of reading the system clock, a headless run (and a test) controls time completely. That's why the recording on the right is identical every time we render it.

What you should know now

You can now do, unaided

  • Turn a folder of Rust source into a standalone executable, say where cargo put it, and explain why it runs on a machine without Rust.
  • Wrap that executable into a signed .app by hand, and read any .app's Info.plist to see what it runs.
  • Build a screen from state with rows, columns and keys, and predict which elements will travel and which will swap in place.
  • Choose a spring or a transition by feel, and explain why a spring survives a double tap.
  • Write a headless test that drags an element and asserts on both state and pixels.
  • Add a GPU effect to a view by reserving a slot and feeding it four numbers.

Now true about this codebase

  • Every file in tutorial/src/bin/ is its own program, and rune_tutorial::gfx is the only shared code.
  • The compositor's marks table (FIRE = 1, LENS = 2, SHOCK = 3) is the contract between views and effects. Adding an effect means a new mark and a new layer arm, and nothing in the views.
  • Every snippet on this page is extracted from code that compiles. Edit the .rs, not the HTML.

Check yourself

  1. A friend's copy of your .app opens, but on their Intel Mac it says "bad CPU type". What did you build for, and what would you change?
  2. A list reorder looks like the text "flickers" instead of rows moving. What's your first grep?
  3. A progress ring you added makes the laptop fan spin even when idle. Which function do you open first?

Advanced techniques & alternate solutions

Bundling: cargo-bundle or Rune's scripts/mac-app

cargo install cargo-bundle     # reads [package.metadata.bundle] from Cargo.toml
cargo bundle --release --bin l2_queue

It wins when you ship to several platforms (it also makes .deb and .msi) and want the metadata in Cargo.toml. Rune's scripts/mac-app wins on a Mac you're iterating on: it relaunches without the window blinking and keeps permissions. Our 20-line script is worse for shipping but better for learning, because there's nothing in it you can't read. The crossover is the first time you need an icon.

Animating by hand from poll

fn poll(s: &mut State, now: f64, _: &mut Tx) -> bool {
    s.x += (target(s) - s.x) * 0.2;   // a hand-rolled ease, every frame
    true
}

Worse here: it ties motion to frame rate, loses velocity on retarget, and rebuilds the view every frame. It wins when the motion is the content, like a physics toy or a game loop, where you need full control of every step. The falling todo in the repo's own "floor is lava" experiment does exactly this. It also has to call tx.instant() in poll, because Rune would otherwise spring-smooth every keyed position it sets by hand.

Keeping decisions in handlers

For a two-line app with no tests, an inline if in the handler is fine, and extracting release would be ceremony. The crossover is the first time you want to test the rule, or a second gesture (a keyboard shortcut, say) needs the same decision.

Considered and rejected for this page: the web build

Rune can target one WebGPU canvas, which would make these examples interactive in the page. When we tried it, Chrome and Helium clipped the canvas and dropped the effects. Recordings of the real native build were the approach we could verify end to end.

Reference

Common patterns

  • Calculation returns new data → handler assigns it (s.queue = play_next(&s.queue, id)).
  • Key by identity: .key(format!("track-{}", track.id)).
  • Drag: Move sets an offset, and Up asks a calculation and applies its answer.
  • Time: poll copies now, and handlers store start times.
  • Effect: rune::effect(MARK).effect_data([..]).absolute(..).size(..), plus run_with.

Key takeaways

  • target/release/<name> is the program, and a .app is a folder around it.
  • The view is a calculation by type, and the compiler keeps it pure.
  • Motion is a property (a spring), never a script.
  • Inject the clock and the pointer, and everything becomes testable.

Troubleshooting

Problem: error[E0599]: no method named … for struct El.
Solution: rev drift, or a typo. Check the drift check, then the method list in Rune's crates/rune/README.md at the pinned rev.

Problem: the first build fails while compiling objc2 or metal.
Solution: run xcode-select --install (Command Line Tools).

Problem: --video fails at once.
Solution: ffmpeg isn't on PATH (brew install ffmpeg).

Problem: text sits under the traffic lights.
Solution: windows draw under the titlebar, so add .pt(40.0) to your root column.

Problem: springs snap instantly in a window but glide in headless recordings.
Solution: macOS Reduce Motion is on (System Settings → Accessibility → Display). Rune honours it by snapping travel to a short fade. Headless runs don't read it.

Problem: a dark box trails a glass shape.
Solution: the lens shadow, so set shadow: 0.0 in its LensParams.
